# Component 5.1 — Campaign Brief Assembler

**Deterministic.** No LLM. Builds the immutable campaign brief from approved signal + district + reason codes. Runs validation checks before declaring the brief complete.

## Purpose

Produce the single artifact every downstream component reads from. Once written, immutable for the campaign's lifetime.

## Trigger

Fires on `campaign_workspaces` row creation (Gate 1 approval). Runs synchronously.

## Inputs

- `campaign_workspaces` row (just created, status = `pending_content`)
- `signal_queue` — the originating signal
- `signal_briefs` — the approved brief (for context, not as source of evidence)
- `districts` — district master record
- `signal_queue` (historical) — for `campaign_history` lookup

## Outputs

- `campaign_workspaces.campaign_brief` (JSONB) — full immutable brief
- `campaign_workspaces.status` updated to `in_content_preparation` (on validation pass) or `content_preparation_failed` (on validation fail)

See `schemas/campaign-brief.md` for the output schema.

## Assembly steps

1. Read the workspace and resolve foreign keys: signal, brief, district.
2. Build the `district` sub-object from `districts` table.
3. Build the `target_contacts` array from the originating signal's `contact_hints`. v1: pass through as-is; not enriched.
4. Build the `originating_signal` sub-object with verbatim evidence (NEVER paraphrased) from the signal.
5. Build the `campaign_history` array from prior workspaces at the same district (last 12 months, max 5 entries).
6. Build the `reason_codes` array — copy from the originating signal.
7. Build the `urgency` sub-object — copy from the originating signal.
8. Run validation checks (see below).
9. If all checks pass, write `campaign_brief` to the workspace and update status to `in_content_preparation`. Immediately trigger 5.2 Asset Selector.
10. If any check fails, write the failure detail to `campaign_workspaces.metadata.validation_failures`, set status to `content_preparation_failed`, raise an alert.

## Validation checks (deterministic)

These are NOT compliance checks. They are input hygiene to catch malformed briefs before they hit Writing Studio.

| Check | Logic | Why |
|---|---|---|
| `evidence_present` | `originating_signal.verbatim_snippet` is non-empty (≥ 20 characters) | Writing Studio anchors on evidence. Missing evidence → hallucinated outreach. |
| `reason_codes_in_registry` | Every code in `reason_codes` exists in `reason_code_registry` AND is not deprecated | Prevents drift if registry codes change. |
| `campaign_type_approved` | `campaign_type` ∈ `{OBC, biliteracy, dyslexia, general_growth}` | v1 hardcoded list. Extend when new rulesets ship. |

Compute these and store as a `validation` sub-object in the brief:

```json
{
  "validation": {
    "passed": true,
    "checks": {
      "evidence_present": true,
      "reason_codes_in_registry": true,
      "campaign_type_approved": true
    }
  }
}
```

If `passed: false`, set workspace status to `content_preparation_failed` and do NOT proceed to 5.2.

```
synchronously, immediately after Gate 1 approval.

Operating principles:

1. VALIDATION FIRST, ALWAYS.
   Run all validation checks before writing the brief. If any check fails, write

2. FROZEN EVIDENCE ONLY.
   The originating_signal.verbatim_snippet must be copied exactly — never

   this evidence. Any alteration creates hallucination risk.

3. FAIL LOUDLY.
   A validation failure here is better than a silently malformed campaign. Report
   which check failed, the specific field value that failed it, and what a valid
   value would look like. Alerts go to the operator, not just logs.

4. DETERMINISTIC ONLY.
   No LLM calls. No inference. No interpretation. Every field in the brief is
   a direct copy or deterministic transform of the input data. If a field cannot
   be populated from the inputs, it is null — not invented.

5. IMMUTABILITY.
   Once written, the brief cannot be modified. If an error is discovered after
   write, the workspace must be rejected and re-created from Gate 1.

Output: campaign_workspaces.campaign_brief (JSONB), status updated to
in_content_preparation on success or content_preparation_failed on any validation failure.
```

## Immutability rule

After 5.1 writes the brief, **no subsequent agent (including 5.2, 5.3, or human edits) may modify it**. If a human discovers an error post-assembly, the entire workspace must be rejected and re-created from a re-approved brief at Gate 1.

Enforce at code level: `campaign_brief` reads return a frozen dataclass; mutation attempts raise. Enforce at DB level via row trigger that rejects UPDATE on `campaign_brief` after initial INSERT.

## Failure modes

- **District record missing** — should be impossible (foreign key constraint on workspace creation), but if it happens: alert, mark failed.
- **Signal has empty verbatim_snippet** — validation check fails. This is an upstream scout bug — the signal should never have been emitted. Mark workspace failed, alert with link to originating signal.
- **Reason code deprecated since signal was emitted** — validation check fails. Operator must either un-deprecate the code or reject the workspace.

## DB tables touched

- `campaign_workspaces` (read + write)
- `signal_queue` (read)
- `signal_briefs` (read)
- `districts` (read)
- `reason_code_registry` (read)

## Implementation notes for Codex

- This is a pure-function transform with a couple of DB reads. Test it independently of any downstream component.
- Use Pydantic for the `CampaignBrief` model. Make it `frozen=True` so accidental mutation fails loudly.
- The DB row trigger to enforce immutability is one of:

```sql
CREATE OR REPLACE FUNCTION enforce_brief_immutability()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.campaign_brief IS NOT NULL AND NEW.campaign_brief IS DISTINCT FROM OLD.campaign_brief THEN
    RAISE EXCEPTION 'campaign_brief is immutable once set';
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_brief_immutable
BEFORE UPDATE ON campaign_workspaces
FOR EACH ROW EXECUTE FUNCTION enforce_brief_immutability();
```

- Brief assembly is fast (< 100ms). Synchronous is fine. No need for queue here.
