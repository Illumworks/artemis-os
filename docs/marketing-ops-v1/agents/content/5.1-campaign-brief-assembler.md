# Component 5.1 — Campaign Brief Assembler

Builds the campaign initiation proposal from an already-grouped candidate signal cluster, then hands the confirmed campaign into downstream content preparation. In CI2 this component's first job is to emit a strictly valid `CampaignInitiationProposal` JSON object.

## Purpose

Read the full candidate signal cluster and propose the campaign identity the operator will confirm or edit: name, one-line objective, recommended deliverable mix, target scope, and rationale grounded in the evidence and predecessor campaign history.

## Trigger

Fires on `campaign_workspaces` row creation (Gate 1 approval). Runs synchronously.

## Inputs

- `campaign_candidates` row (already created by deterministic cluster-or-create)
- `campaign_candidate_signals` join rows — the FULL signal cluster, not just the primary
- `signal_queue` — each cluster signal's evidence
- `deliverable_types` — active registry slugs
- predecessor campaign context when `campaign_candidates.predecessor_id` is set:
  prior candidate name/objective, latest brief, linked collateral

## Outputs

- `campaign_candidates.initiation_proposal_json` (JSONB) — the pending proposal
- no campaign initiation side effect; operator confirmation later calls `initiate_campaign`

Exact output schema:

```json
{
  "name": "Fort Bend Biliteracy Follow-Up",
  "objective": "Build on the prior district outreach with a timely follow-up about the new multilingual rollout.",
  "recommended_deliverable_types": ["outreach_email"],
  "target_scope": {"mode": "states", "states": ["TX"]},
  "rationale": "The cluster combines corroborating district signals and the prior campaign already established a relevant thread."
}
```

## Assembly steps

1. Read the candidate and the FULL attached signal cluster.
2. Identify the primary signal, but use all cluster signals as evidence when proposing the campaign.
3. If `predecessor_id` is present, ground the proposal on the predecessor's name, objective, latest brief, and linked collateral. Continue the thread; do not restart from zero.
4. Default `recommended_deliverable_types` to `["outreach_email"]` unless the cluster clearly supports another ACTIVE registry slug.
5. Default `target_scope` from the primary signal's resolved district state as `{"mode":"states","states":[...]}`. If the district is unresolved, use `{"mode":"all_districts"}`. Never invent a state.
6. Return exactly one JSON object matching `CampaignInitiationProposal`.
7. Do NOT call `initiate_campaign`, do NOT split or regroup signals, and do NOT kick off content generation yourself. The operator confirms the proposal later.

## Validation checks (deterministic)

These are NOT compliance checks. They are output-shape checks before the pending proposal is persisted.

| Check | Logic | Why |
|---|---|---|
| `name_present` | `name` is non-empty and human-readable (1..120 chars) | The operator needs a real campaign identity to confirm or edit. |
| `objective_present` | `objective` is non-empty (1..500 chars) | Avoids silent empty proposals. |
| `deliverable_types_active` | every `recommended_deliverable_types` slug is ACTIVE in `deliverable_types` | Registry truth; invalid slugs trigger self-teaching retry. |
| `target_scope_valid` | `target_scope` matches the exact `TargetScope` schema | No fabricated targeting. |

Compute these and store as a `validation` sub-object in the brief:

If validation fails, the caller will retry once with the validation error. Do not emit partial JSON and do not emit prose outside the JSON object.

```
Use this mode when the runtime task explicitly asks for a

6. NO TOOL CALLS IN PROPOSAL MODE.
   In proposal mode you are returning JSON for the caller to validate and
   persist. Do NOT call `campaign_brief.read` or `campaign_brief.write` here.

Use this mode when the runtime task is to assemble or persist the downstream
campaign brief for content preparation.

1. GROUND ON THE EXISTING BRIEF STATE FIRST.
   - If context includes `campaign_brief_id`, call
     `campaign_brief.read({"brief_id": <campaign_brief_id>})`.
   - Otherwise, if context includes `campaign_candidate_id`, call
     `campaign_brief.read({"candidateId": <campaign_candidate_id>})` when you
     need the latest persisted brief for that candidate.

2. ASSEMBLE THE EXACT BRIEF JSON.
   Build the immutable brief content from the candidate context, signal
   evidence, qualification data, predecessor context, and linked assets.
   Never invent missing fields.

3. PERSIST WITH THE TOOL, NOT WITH PROSE.
   Call `campaign_brief.write` with:
   - `candidateId` = `campaign_candidate_id` from runtime context
   - `content` = the complete assembled brief JSON object

4. WRITE ONCE, THEN REPORT THE RESULT.
   After the tool call succeeds, report the returned `brief_id` and a one-line
   summary of what was persisted. Do not pretend the brief is saved unless the
   tool call actually returned success.

5. NEVER MUTATE BY HAND.
   Do not describe a database update, do not suggest Bash, SQL, or HTTP, and do
   not output a "would write" placeholder. Use the MCP tool call.
```

## Tools required

```python
# Reads the current immutable brief state when the runtime task requires it.
campaign_brief.read(brief_id: int) -> {
  "id": int,
  "candidate_id": int,
  "content": dict,
  "generated_by": str,
  "generated_at": str | null,
}
campaign_brief.read(candidateId: int) -> same payload as above for the latest brief

# Persists the downstream immutable campaign brief for a candidate.
campaign_brief.write(candidateId: int, content: dict) -> {
  "brief_id": int,
  "status": "written",
}
```

## Immutability rule

After 5.1 writes the brief, **no subsequent agent (including 5.2, 5.3, or human edits) may modify it**. If a human discovers an error post-assembly, the entire workspace must be rejected and re-created from a re-approved brief at Gate 1.

Enforce at code level: `campaign_brief` reads return a frozen dataclass; mutation attempts raise. Enforce at DB level via row trigger that rejects UPDATE on `campaign_brief` after initial INSERT.

## Failure modes

- **District record missing** — should be impossible (foreign key constraint on workspace creation), but if it happens: alert, mark failed.
- **Signal has empty verbatim_snippet** — validation check fails. This is an upstream scout bug — the signal should never have been emitted. Mark workspace failed, alert with link to originating signal.
- **Reason code deprecated since signal was emitted** — validation check fails. Operator must either un-deprecate the code or reject the workspace.

## DB tables touched

- `campaign_workspaces` (read + write)
- `signal_queue` (read)
- `signal_briefs` (read)
- `districts` (read)
- `reason_code_registry` (read)

## Implementation notes for Codex

- This is a pure-function transform with a couple of DB reads. Test it independently of any downstream component.
- Use Pydantic for the `CampaignBrief` model. Make it `frozen=True` so accidental mutation fails loudly.
- The DB row trigger to enforce immutability is one of:

```sql
CREATE OR REPLACE FUNCTION enforce_brief_immutability()
RETURNS TRIGGER AS $$
BEGIN
  IF OLD.campaign_brief IS NOT NULL AND NEW.campaign_brief IS DISTINCT FROM OLD.campaign_brief THEN
    RAISE EXCEPTION 'campaign_brief is immutable once set';
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_brief_immutable
BEFORE UPDATE ON campaign_workspaces
FOR EACH ROW EXECUTE FUNCTION enforce_brief_immutability();
```

- Brief assembly is fast (< 100ms). Synchronous is fine. No need for queue here.
