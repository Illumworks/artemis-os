# Agent 2.1 — Cross-Reference Agent

The qualification engine. Takes one signal at a time from `signal_queue`, runs it through three phases, writes the result.

## Purpose

Decide:
1. Does this signal pass hard filters? (Deterministic.)
2. How well does it match each campaign type? (Mostly deterministic; LLM for qualitative rubrics.)
3. Which campaign type(s) should it route to, if any?

## Cadence

Polls `signal_queue` every 5 minutes for rows with `status = 'pending_qualification'`. Processes in batches up to 50 signals per poll cycle.

## Three phases

### Phase 1 — Hard filters (deterministic)

For each signal, run hard filter checks from every active ruleset. **No LLM calls.** If any hard filter fails, the signal is immediately rejected — no Phase 2 cost incurred.

Common hard filters (from `rulesets/obc.yaml` and others):

| Filter | Check | Source |
|---|---|---|
| `priority_state` | `signal.geography.state IN territory_config.priority_states` | Territory Config |
| `district_min_enrollment` | `district.enrollment >= 5000` | districts table |
| `has_contact_or_stub` | `contact_db_stub.has_contact(district_id)` | Contact DB stub |

**Output of Phase 1:** `passed_hard_filters: bool`.

If False, update signal status to `rejected_hard_filter` and STOP. Record which filter failed in `signal_queue.signal->metadata.rejection_reason`.

### Phase 2 — Score against ALL rulesets

For each active ruleset (e.g., OBC, biliteracy, dyslexia), compute a fit score:

1. **Weighted signals (deterministic).** For each weighted signal rule, run the check SQL. If it fires, add its weight (or per-mention weight up to cap) to the running score.
2. **Qualitative rubrics (LLM).** For each rubric in the ruleset, run a single LLM call with the rubric prompt template + signal evidence. If `applies=true` AND `confidence >= applies_threshold`, add `weight_when_fires` to the running score.
3. **Normalize.** Apply the ruleset's `fit_score_formula` to produce a 0–1 score.

Run this for **every active ruleset**, not just the most relevant. A signal may match multiple campaign types.

**Output of Phase 2:**
```json
{
  "ruleset_scores": [
    {
      "ruleset_id": "OBC",
      "fit_score": 0.82,
      "evidence": [
        {"rule_id": "obc_w5", "fired": true, "contribution": 0.25},
        {"rule_id": "obc_q1", "applies": true, "confidence": 0.85, "reasoning": "...", "contribution": 0.20}
      ]
    },
    {"ruleset_id": "general_growth", "fit_score": 0.71, "evidence": [...]},
    {"ruleset_id": "biliteracy", "fit_score": 0.12, "evidence": [...]},
    {"ruleset_id": "dyslexia", "fit_score": 0.05, "evidence": [...]}
  ]
}
```

If the highest fit_score is < 0.4 across all rulesets, update status to `rejected_low_fit` and STOP. Skip Phase 3.

### Phase 3 — Route to top campaign type(s) (deterministic)

For each ruleset above the routing threshold:

1. Primary: highest score >= `primary_threshold` (default 0.7).
2. Secondary: next-highest score >= `secondary_threshold` (default 0.6), subject to redundancy rules in the ruleset.

If no ruleset scores >= primary_threshold, signal is qualified but campaign assignment is `general_growth` fallback. (`// JUDGMENT CALL:` may want to reject these instead of routing to general_growth. Tune after first 100 signals.)

**Output of Phase 3:**
```json
{
  "primary_campaign_type": "OBC",
  "primary_score": 0.82,
  "secondary_campaign_types": [
    {"type": "general_growth", "score": 0.71}
  ]
}
```

Update signal status to `qualified`. Phase 3 output is passed to Brief Composer immediately (in-memory, not via queue — Brief Composer runs right after Phase 3 completes).

## Inputs

- `signal_queue` — read pending signals
- `ruleset_storage.list_active()` — all active rulesets
- `districts` — read for hard filter checks
- `signal_queue` (historical) — read for "prior signals at this district" rules
- `contact_db_stub.has_contact()` — for the contact filter

## Outputs

- `signal_queue` status update (one of: `rejected_hard_filter`, `rejected_low_fit`, `qualified`)
- `signal_queue.signal->metadata.qualification_result` — full Phase 2 + Phase 3 output for auditability
- In-memory Phase 3 result passed directly to 2.4 Brief Composer

## Prompt scaffolding (Phase 2 qualitative rubric)

```
You are evaluating ONE qualitative rubric against ONE signal's evidence.

Apply the rubric strictly. Do not stretch interpretation.
False positives cost more than false negatives — when in doubt, return applies=false.

RUBRIC: "{{rubric.description}}"

EVIDENCE:
{{signal.source.verbatim_snippet}}

SPEAKER: {{signal.source.speaker_attribution}}
SOURCE: {{signal.source.type}}, {{signal.source.url}}

Return JSON ONLY (no preamble, no markdown fence):
{
  "applies": true|false,
  "confidence": 0.0-1.0,
  "reasoning": "1 sentence explaining your decision"
}
```

## Failure modes

- **No active rulesets** — log CRITICAL, do not process signals. Operator must seed at least one ruleset.
- **Ruleset hard filter SQL fails to compile** — should never happen post-compiler. If it does, alert and skip the ruleset (continue with others).
- **LLM call timeout / error during qualitative rubric** — retry once. On second failure, treat rubric as `applies=false` and log the failure. Do not block the whole signal on one bad rubric.
- **Signal references district that no longer exists** — write to `unresolved_signals`, set signal status to `rejected_hard_filter` with reason `district_not_found`.

## DB tables touched

- `signal_queue` (read + update)
- `ruleset_versions` (read active versions)
- `districts`, `district_aliases` (read)
- `unresolved_signals` (write rare)

## Implementation notes for Codex

- **Cost shape:** Phase 1 = ~$0 per signal (DB queries only). Phase 2 = ~$0.001–0.01 per signal (1 LLM call per rubric per ruleset; with 4 rulesets × 2 rubrics each = 8 LLM calls). Phase 3 = ~$0 (deterministic). Budget alarm if total cost-per-signal exceeds $0.10.
- Use Claude Haiku for qualitative rubrics by default; bump to Sonnet only when the rubric explicitly tags `model: sonnet` in YAML (rare, used for high-stakes rubrics).
- Phase 2 can parallelize rubric evaluation across rulesets. With 4 rulesets × 2 rubrics each, fire 8 LLM calls concurrently per signal. Cuts wall-clock time roughly 8x.
- Phase 2 stores **every rubric outcome** in the signal's metadata for auditability. This is the raw material the Ruleset Manager Agent uses when proposing improvements.
- Process signals in batches of up to 50 per poll cycle. Use SELECT FOR UPDATE SKIP LOCKED so multiple worker instances don't conflict (preparing for v2 scale-out).
- Pseudocode:

```python
def run_qualifier_cycle():
    signals = signal_queue.read_pending(limit=50)
    rulesets = ruleset_storage.list_active()
    for sig in signals:
        phase1 = run_hard_filters(sig, rulesets)
        if not phase1.passed:
            signal_queue.update_status(sig.signal_id, 'rejected_hard_filter', reason=phase1.failed_filter)
            continue
        phase2 = run_scoring(sig, rulesets)  # parallelize internally
        if max(s.fit_score for s in phase2.ruleset_scores) < 0.4:
            signal_queue.update_status(sig.signal_id, 'rejected_low_fit')
            continue
        phase3 = run_routing(phase2)
        signal_queue.update_status(sig.signal_id, 'qualified')
        brief_composer.compose(sig, phase2, phase3)  # synchronous
```
