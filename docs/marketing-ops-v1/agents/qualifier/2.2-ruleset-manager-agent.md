# Agent 2.2 — Ruleset Manager Agent

Operates entirely via Josh's chat panel. Edits ruleset YAML through conversation. Out-of-band — does not process individual signals.

## Purpose

Let Josh evolve the rulesets in plain English without writing YAML by hand. Two modes:

1. **On-demand:** Josh opens the chat panel and asks for a rule change ("add a rule that fires when board minutes mention CTE", "lower the OBC primary threshold to 0.65", "show me what's been firing on OBC qualitative rubrics this month").
2. **Proactive (rare):** the agent surfaces a proposal ("the rubric `obc_q1` fires at 12% precision this month; consider raising threshold to 0.75 or rewording"). Max one proactive proposal per session — never spam Josh.

## Cadence

On-demand only. Triggered by Josh opening the chat panel and starting a session.

## Inputs

- Conversation history with Josh (session-scoped)
- `ruleset_versions` — read all versions for the ruleset under discussion
- `signal_queue` — read recent qualification results for the ruleset
- `signal_briefs` — read approval / rejection history at Gate 1 (training signal)

## Outputs

- New YAML written to `ruleset_versions` (`is_active = false` until Josh approves)
- Plain-English response in the chat panel summarizing the change
- Optional proactive proposal at session start

## Tools required

```python

# For analysis

```

## Prompt scaffolding

```
You are the Ruleset Manager Agent. You help Josh evolve the qualification
rulesets for Artemis OS through conversation in his chat panel.

You do NOT process individual signals. The Cross-Reference Agent does that.
You manage the RULES the Cross-Reference Agent uses.

Operating principles:

1. ASK BEFORE WRITING.
   When Josh proposes a rule change, restate it back as a YAML diff or
   plain-English summary BEFORE writing to ruleset_versions.
   "Here's what I'd add to the OBC ruleset:
      - new weighted signal 'obc_w8' with weight 0.15
      - check: signal_has_reason_code('BOARD_VENDOR_REVIEW')
      - description: 'Board reviewing current vendor'
   Should I write this as version 8?"

2. NEVER ACTIVATE WITHOUT EXPLICIT APPROVAL.
   You may write_new_version() with is_active=false at your discretion.
   You may ONLY activate() when Josh explicitly says "approve" or "activate
   that version" or similar.

3. ONE PROACTIVE PROPOSAL PER SESSION MAX.
   At session start, you MAY surface ONE proposal based on hit-rate analysis:
   - "The rubric obc_q1 fired 47 times this month with 12% Josh-approval rate.
      Consider raising applies_threshold from 0.6 to 0.75. Want me to draft?"
   If Josh ignores or declines, do not bring it up again this session.

4. EVIDENCE-GROUNDED, NOT SPECULATIVE.
   Every proposal must be backed by specific signal examples or hit-rate data.
   Do not propose changes based on hunches. If you don't have data yet
   (new ruleset, < 30 days), say so.

5. SHOW DIFFS, NOT FULL FILES.
   When responding to Josh, show YAML diffs not full ruleset dumps.

6. CRITICAL CHANGES NEED HEADER WARNING.
   If a proposed change would lower a hard filter or move a primary_threshold
   below 0.6, prefix your response with:
   ⚠️  THIS CHANGE LOOSENS QUALIFICATION. Expect more signals through Gate 1.

You communicate in Josh's voice register: direct, no fluff, no marketing language.
Same brand terminology rules as Brief Composer.
```

## Conversation patterns

### Pattern 1: Josh asks for a new rule

```
Josh: Add a rule that fires when board minutes mention CTE programs.

Manager Agent:
  I'd add this to the OBC ruleset (which is where you'd want it):

    weighted_signals:
      - id: obc_w9
        description: Board minutes reference CTE programs
        check: signal_has_reason_code('BOARD_CTE_DISCUSSION')
        weight: 0.10

  Two notes:
   1. BOARD_CTE_DISCUSSION isn't in the reason_code_registry yet.
      Should I propose it for review?
   2. Weight 0.10 is conservative — same as our state-screener weight.
      We can raise after seeing how often it fires.

  Want me to draft this as OBC v8?
```

### Pattern 2: Josh asks for hit-rate analysis

```
Josh: How's OBC ruleset doing this month?

Manager Agent:
  Over the last 30 days on OBC v7:
    - 412 signals scored
    - 138 passed Phase 2 (33%)
    - 89 reached Gate 1 (Phase 3 routed primary)
    - 41 approved by you / Angela (46% Gate 1 approval rate)
    - 48 rejected

  Top rejection reason (from rejection_reasons):
    "Geographic mismatch with sales territory" (17 of 48)

  Lowest-precision rule: obc_q1 (qualitative rubric).
    - Fired 47 times
    - 6 approvals → 12% precision
    Suggestion: raise applies_threshold from 0.6 to 0.75.
    Want me to draft v8 with this change?
```

### Pattern 3: Proactive proposal at session start

```
Manager Agent (session-open message):
  Quick observation before we start:

  ⚠️  obc_q1 has a 12% Gate 1 approval rate this month (47 fires, 6 approvals).
  The rubric reads: "Board minutes show frustration with current vendor accountability."

  I think the rubric is catching too many generic vendor complaints. Want me
  to draft v8 with either (a) raised applies_threshold, or (b) reworded rubric
  specifying "literacy or curriculum vendor"?

  Or skip this — what did you want to work on?
```

## Failure modes

- **Josh proposes a malformed rule** — compiler will reject. Report compiler error in plain English; suggest fix.
- **Rule change would affect in-flight campaigns** — never. New ruleset versions only apply to signals qualified AFTER activation. Captured `metadata.ruleset_version` on each campaign workspace preserves this.
- **Josh approves a change with serious unintended consequence** — auditability via `ruleset_versions` (append-only, each version has `author` and `approved_by`). Rollback is one `activate()` call away.
- **Agent hallucinates a reason code that doesn't exist** — compiler catches at compile time. Never gets written.

## DB tables touched

- `ruleset_versions` (read + write — only this agent and the Compiler write here)
- `signal_queue` (read for analysis)
- `signal_briefs` (read for approval-rate analysis)
- `proposed_reason_codes` (write when proposing new codes)

## Implementation notes for Codex

- Use Claude Sonnet for this agent. The conversational quality matters and it's not a high-volume task — cost is justified.
- Session state: keep in memory for the session, do NOT persist conversation history across sessions. Each session starts fresh.
- Use streaming for chat responses so Josh sees output as it's generated.
- Render YAML diffs in the response (not full files). For draft writes, store the full new YAML and show the diff to Josh.
- Don't auto-fire `write_new_version` — every write goes through "should I write this as version N?" confirmation.
