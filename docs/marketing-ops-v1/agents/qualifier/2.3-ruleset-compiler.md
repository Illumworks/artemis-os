# Component 2.3 — Ruleset Compiler

**Deterministic.** No LLM. Converts YAML ruleset definitions into executable runtime objects.

## Purpose

Validate ruleset YAML, compile it to a CompiledRuleset object, and persist to `ruleset_versions`.

This is a pure-function transform plus DB writes. There is no agent loop, no chat, no LLM. It is invoked synchronously by the Ruleset Manager Agent (or by the seed scripts during DB init).

## Trigger

Called whenever a new ruleset YAML is written. Two entry points:

1. **Seed init** — at DB setup, compile `rulesets/obc.yaml`, `rulesets/biliteracy.yaml`, `rulesets/dyslexia.yaml`. Activate all three at version 1.
2. **Ruleset Manager Agent** — after Josh approves a draft, the agent calls `compile_and_write(ruleset_id, yaml_source, author)`.

## Compilation steps

1. **Parse YAML.** If parse fails, raise `CompilationError("YAML parse error: ...")`.
2. **Schema validation.** Top-level keys: `ruleset_id`, `version` (advisory; compiler overrides with next-available), `description`, `focus_areas`, `hard_filters`, `weighted_signals`, `qualitative_rubrics`, `fit_score_formula`, `routing`. Reject unknown top-level keys.
3. **Hard filter validation.** Each filter:
   - Must have `id`, `type='deterministic'`, `check`, `fail_action`
   - `check` must compile as Python expression or SQL (depending on form)
   - `fail_action` must be `reject_signal`
4. **Weighted signal validation.** Each:
   - Must have `id`, `description`, `check`, `weight`
   - `weight` is float, 0 < weight <= 1.0
   - `check` SQL must compile cleanly (run `EXPLAIN` on parameterized version)
   - If `signal_has_reason_code(...)` is used, the argument must exist in `reason_code_registry`
   - Optional: `per_mention: true` + `cap` for capped repeated-fire rules
5. **Qualitative rubric validation.** Each:
   - Must have `id`, `description`, `prompt`, `fires_when`, `weight_when_fires`
   - `prompt` must compile as Jinja2 template
   - `fires_when` parses to: `applies == true AND confidence > X` (only this form supported in v1)
   - `weight_when_fires` is float 0 < weight <= 1.0
6. **Fit score formula validation.** Parse the formula expression; check it references only declared rules.
7. **Routing validation.** `primary_threshold >= secondary_threshold`. Both in (0, 1].
8. **Weight sanity check.** Sum of all positive `weight` and `weight_when_fires` values must not exceed 2.0 (post-normalization, the formula handles this; the cap is a sanity guard against typo'd 10.0 weights).
9. **Reason code cross-check.** Every `signal_has_reason_code('...')` argument must exist in `reason_code_registry` AND not be deprecated. If not, raise CompilationError listing missing codes.
10. **Version assignment.** Query `ruleset_versions` for max version of this `ruleset_id`; increment.
11. **Write.** INSERT into `ruleset_versions` with `is_active = false`.

## What the compiler stores

```python
@dataclass
class CompiledRuleset:
    ruleset_id: str
    version: int
    description: str
    focus_areas: list[str]
    hard_filters: list[CompiledHardFilter]
    weighted_signals: list[CompiledWeightedSignal]
    qualitative_rubrics: list[CompiledRubric]
    fit_score_formula: str  # compiled / normalized form
    routing: RoutingConfig
    yaml_source: str        # original YAML, kept for audit
    compiled_at: datetime
    author: str
```

Stored as JSONB in `ruleset_versions.compiled`.

## Failure modes

- **YAML parse error** → `CompilationError("YAML parse error: ...")`, raised before any DB write
- **SQL doesn't compile** → `CompilationError("Rule {rule_id}: SQL does not compile: ...")`
- **Reference to nonexistent reason code** → `CompilationError("Rule {rule_id}: reason code 'XXX' does not exist in registry")`
- **Weight sum > 2.0** → warn loudly, but allow (operator may know what they're doing)
- **Jinja2 template parse error** → `CompilationError("Rubric {rubric_id}: prompt template does not parse: ...")`

All errors must be human-readable. Output is presented in the Ruleset Manager Agent's chat panel — Josh sees these directly.

## DB tables touched

- `ruleset_versions` (write)
- `reason_code_registry` (read for validation)

## Implementation notes for Codex

- Use PyYAML for parsing.
- Use Jinja2 for rubric prompt templates.
- For SQL `check` validation: prepare the statement with placeholders for `:district_id`, `:signal_id`, etc., and run `EXPLAIN`. If `EXPLAIN` succeeds, SQL is structurally valid.
- For Python-expression `check` validation: use `ast.parse()` with a restricted node whitelist (no `Call` except to a small allow-list of functions like `signal_has_reason_code`).
- The compiler is the security boundary. **Never execute YAML-supplied code directly.** All `check` expressions must go through the compiler's restricted evaluator at runtime, not `eval()`.
- Compiled rulesets are cached in process memory by Cross-Reference Agent. Cache invalidation on `activate()` is via a PostgreSQL NOTIFY/LISTEN channel — simple, no extra infrastructure.
