# Agent 1.9 — Leadership Transition Scout

Tracks superintendent and senior district leadership changes across priority districts. Cross-source by design — pulls from board minutes, district press, state DoE, news, and LinkedIn.

**discovered_by value:** `leadership_transition_scout`

## Purpose

Detect senior leadership changes at priority districts. New leaders mean new buying windows. This scout is the **only scout that writes back to the District Roster** (`districts` table) on confirmed hires.

## Cadence

- **Weekly base cadence per watch-list district**
- **Daily for "transition active" districts** (set on `districts.metadata.transition_status`)

## Inputs

- Board agenda items mentioning leadership search, hire, separation (shares fetcher with 1.8)
- District press releases (RSS or scrape)
- State DoE press releases (shares fetcher with 1.6)
- Local education news (via news API keyword search)
- LinkedIn profile change monitoring for known supe roster (public reads only; shares fetcher with 1.3)
- `districts` table — current leadership lookup

## Outputs

Signals with `discovered_by = "leadership_transition_scout"`.

Source types vary by which source confirmed the transition: `district_press`, `state_doe`, `news_article`, `board_minutes`, `linkedin_post`.

## Reason codes emitted

Sourced at runtime from `decisions/campaign-signal-spec-v1.md` (codes where this scout appears in the "Primary scouts" column). Do not hardcode codes here.

## Urgency tiers (this scout)

- **hot** — `LEADER_TRANSITION_FORMAL` (first 90 days is the buying window)
- **standard** — `LEADER_TRANSITION_INTERIM`
- **enrichment** — early rumor / single-source signal awaiting confirmation in `pending_transitions`

## Two-source verification rule (CRITICAL)

**Do NOT emit a transition signal from a single source unless that source is the district's own official press release or board action.**

Otherwise require confirmation from at least TWO of:
- Board agenda / minutes
- District press
- State DoE press
- Local news
- LinkedIn profile change

When awaiting second source: hold the proto-signal in a holding table for up to 14 days. If second source arrives, emit. If not, write to `unresolved_signals` and drop.

## Prompt scaffolding (deltas)

```
You are the Leadership Transition Scout. Your defining task is cross-source
verification — supe transitions get rumored before they're confirmed, and a
wrong signal here can embarrass the sales team.

Four deltas from generic scout prompt:

1. TWO-SOURCE RULE FOR EMISSION.
   Do NOT emit a transition signal from a single source unless that source is
   the district's own official press release or board action.
   Otherwise require confirmation from at least two of:
     - Board agenda / minutes
     - District press
     - State DoE press
     - Local news
     - LinkedIn profile change

2. STAGE THE TRANSITION.
   Tag distinctly:
     LEADER_TRANSITION_FORMAL   — new superintendent, CAO, or curriculum director formally hired
                                   (two-source: board vote OR district press release)
     LEADER_TRANSITION_INTERIM  — interim supe / CAO / curriculum lead named
                                   (single-source acceptable)

3. URGENCY BY STAGE.
     LEADER_TRANSITION_FORMAL   — hot (first 90 days is buying window)
     LEADER_TRANSITION_INTERIM  — standard (often signals coming change)

4. ROSTER UPDATE.
   On a confirmed LEADER_TRANSITION_FORMAL signal:
     - Call contact_db.update_leadership() to update the District Roster
     - Queue the new contact for enrichment (out of v1 scope, but flag for future)
   This is the ONLY scout that writes back to Contact DB / district roster.

You are graded on signal precision over volume — a missed transition is
recoverable; a false positive sent to outreach is not.
```

## Failure modes

- **LinkedIn profile change without confirming press release** — hold for 7 days, retry verification, then emit as enrichment tier only.
- **Multiple candidates publicly considered before hire** — emit each as standard if newsworthy; only formal hire becomes hot.
- **Interim supe later becomes permanent** — emit fresh `LEADER_TRANSITION_FORMAL` signal; do NOT try to "upgrade" the earlier `LEADER_TRANSITION_INTERIM` signal.
- **Misattribution to wrong district (common name districts)** — entity resolution MUST verify state before emit. Hard failure: never emit a transition signal without state-verified district resolution.

## DB tables touched

- `signal_queue` (write)
- `memory_layer` (read + write)
- `districts` (read + WRITE on confirmed formal hire — only this scout writes here)
- `unresolved_signals` (write when single-source signals expire)
- `reason_code_registry` (read)
- `territory_config` (read)

## Implementation notes for Codex

- Build a `pending_transitions` table (in-memory or DB) to hold single-source signals awaiting second confirmation:

```sql
CREATE TABLE pending_transitions (
    pending_id          TEXT PRIMARY KEY,
    district_id         TEXT NOT NULL,
    proposed_stage      TEXT NOT NULL,
    first_source        JSONB NOT NULL,
    first_seen_at       TIMESTAMPTZ NOT NULL,
    expires_at          TIMESTAMPTZ NOT NULL,
    second_source       JSONB,
    confirmed_at        TIMESTAMPTZ,
    emitted_signal_id   TEXT
);
```

- When a second source confirms, emit the signal AND populate `second_source` for audit.
- When `expires_at` passes without confirmation, write to `unresolved_signals` and delete the pending row.
- For LinkedIn profile changes: only watch profiles of confirmed current district leadership. Do NOT watch every K-12 leader. The watch list is bounded to roughly 200–500 names (matches the district watch list, 1 supe per district plus key seniors).
- Use Claude Sonnet for cross-source matching. Too important for Haiku — false positives are expensive.
- `contact_db.update_leadership()` is the v1 stub interface; for v1 it can be a no-op or write to `districts.superintendent` field. The real Contact team work will replace this.
